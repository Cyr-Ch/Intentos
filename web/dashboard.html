Connecting

IntentOS gives coding agents the context and checks needed to make changes that belong in a repository. It connects a ticket to code, tests, docs, policy and past decisions, then checks the proposed change before it reaches main.

Who it is for

Teams shipping agent-written changes to an established codebase

Our primary user is a tech lead maintaining a Python library while coding agents work on GitHub issues in parallel. They need the agents to understand rules already encoded in tests and history, recognize vague or already-solved tickets, and keep main healthy when another change lands mid-task.

IntentOS gives that lead a place to inspect the repository's policies and evidence, follow each run, and see why a change was verified, held for review, or refused at merge.

How it works

Evaluation 01 · demandlib

Ticket outcomes and repository rules

Fifteen fresh tickets were run once per arm with the same Codex implementer. The comparison arm also received the verifier and repair loop, so this isolates the value of IntentOS context, planning and coordination more than a raw Codex comparison.

3 / 3Correct routes on clarify or abstain controls; comparison arm 0 / 3
4 vs 8Repair rounds, IntentOS versus comparison arm
21% lessTotal input and output tokens for IntentOS in this run

The comparison arm could not clarify or abstain by construction. Implementation results were close: IntentOS solved 11 of 12 implement tickets and asked for clarification on the twelfth; the comparison arm solved 12 of 12. A blinded model judge counted 5 IntentOS wins, 4 comparison wins and 6 ties before human overrides. One run per ticket limits generalization.

Evaluation 02 · mergeguard

Parallel agent coordination

In a separate fixture evaluation, two clones worked against the same main branch. A change landed while the second agent was working. The Codex gpt-6-astra arm had 15 runs with and without hooks, a PR gate and a guardian.

12 → 0Runs that left main broken, without versus with mergeguard
9 / 9API clashes caught before merge in the rename, parameter and module-move scenarios
3 / 3Semantic meaning changes recovered by the guardian after merge

The harness added 16.2 seconds of wall time per run on average. It did not prevent all bad merges: three reached main before the guardian undid them. The scenario suite is synthetic, and reviewers were simulated.
