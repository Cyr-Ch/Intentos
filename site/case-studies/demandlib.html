Case study 01 · demandlib

Does repository context change what a coding agent does?

A paired, fifteen-ticket comparison of Codex with and without IntentOS context, planning and coordination in the demandlib repository.

27 October 202615 tickets · one run per ticket per armImplementer: gpt-6-astra in both armsBase revision: 32b6cc5

Abstract

IntentOS routed all three clarify-or-abstain controls correctly, used four repair rounds versus eight, and consumed 21% fewer total tokens. Implementation success was the same between IntentOS and the baseline: twelve of twelve tickets resolved in each arm, IntentOS resolving one of them through an accepted clarification rather than a direct diff. The clearest evidence here concerns recognizing when a ticket should not be implemented and carrying repository rules into the first attempt.

1. Study design

Fifteen fresh tickets were prepared for the same demandlib base. The two arms used the same Codex implementer and the same verifier, hidden acceptance tests, invariant checks, scope checks and repair budget. The IntentOS arm additionally received an evidence pack, a planner, a compiled change contract and coordination hooks. The comparison arm received the ticket text only at implementation time.

This comparison arm is not raw Codex: verifier findings, including hidden-test failures, were returned as repair prompts. The first-attempt results are the closest observation of work before that feedback.

Predefined controls. Three tickets required clarification or abstention rather than an unqualified implementation. The comparison arm could not take those routes by construction. The control result therefore measures the effect of the IntentOS routing workflow as well as agent behavior.

The total across all 15 tickets was 21 failed invariant test cases for the comparison and zero for IntentOS. All 21 came from T09, whose project suite passed. The failures were error-message regex mismatches in two overlapping test modules (INV-014 and INV-031): both implementations still rejected invalid non-residential building classes, but only IntentOS preserved the expected wording on its first attempt. The comparison repaired its wording after verifier feedback. These are 21 failed test cases, not 21 distinct broken business requirements.

3. What happened on the tickets

The control cases expose the main behavioral difference. On T05, IntentOS declined to invent a regional-holiday behavior from a vague request. On T06 and T15 it cited existing fixes and abstained. The comparison arm implemented an unspecified seven-file change on T05, changed a warning that did not need a fix on T06, and made no change on T15.

4. Merge outcomes

Branches were considered in ticket order against each arm's own main. IntentOS used a review tier, branch CI, a sync check, merged-result verification and a fast-forward. The comparison arm used a plain merge when its branch project suite was green.

The refusals were textual conflicts or an empty change. No semantic clash reached a merge in this ticket set, and neither arm left main red. These merges therefore do not establish the value of merged-result verification; the separate mergeguard evaluation examines coordination failures.

5. Quality judgement

A blinded, order-swapped model judge scored the paired outputs. The raw tally was 5 IntentOS wins, 4 comparison wins and 6 ties. Four human overrides changed the final tally to 9 IntentOS wins, 0 comparison wins and 6 ties. These are different stages of the evaluation and should be read together.

The T05 override has a recorded rationale: the deliberately underspecified ticket should not have been implemented. The other three overrides (T01, T02 and T14) favor IntentOS without written reasons in the source report; a second model had agreed with the original judge on those three comparisons.

Calibration was model-to-model, not human calibration: a second model scored ten regenerated pairs and agreed with the first judge on seven. The overridden tally is not independent evidence of a general implementation-quality gain.

6. Interpretation and limitations

  • There was one run per ticket per arm. So the differences are not a stable estimate.
  • The tickets and rubric were written by the evaluators before the run. The public repository may have been familiar to the model.
  • The stronger claim from this run is about routing underspecified or already-solved work and reducing repairs. It does not show a general implementation-quality gain.

Takeaway. IntentOS changed which work was attempted, exposed a repository invariant before merge, and reduced repairs and tokens on this batch. Both arms implemented most specified tickets successfully.
