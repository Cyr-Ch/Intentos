Where this started

I interviewed 3 CTOs.

All three work at VC-backed startups with fewer than 10 engineers, trying to move fast.

The shared problem

Coding agents produce changes faster than teams can review them and keep their understanding of the codebase current.

Two causes widen this gap

Parallel development

Agents and engineers duplicate work, miss each other’s decisions, and produce changes that no longer fit together.

Changing business requirements

The business pivots. Old assumptions remain in code and tests, so green tests can still confirm outdated behavior.

The problem in practice

Illustrative scenarios

The solution principle

Make the intent explicit.

Give agents and reviewers a shared, current understanding of what should change, what must keep working, and how to check both.

Parallel development

Keep parallel agents in sync with main.

Changing business requirements

Resolve conflicts between old rules and new requirements.

The review bottleneck

Show reviewers the intent, checks, and open questions.

What we built / How it works

IntentOS

IntentOS gathers rules from history, tests, and docs; clarifies the ticket; keeps agents aligned with main; and independently verifies the implementation and merged result, recording findings for review.

Deployment decisions

The choices and their tradeoffs.

For a small team already using Codex, with private repositories and no GitHub Enterprise.

RequirementWhy it matters to a startup CTODecisionTradeoff
RequirementCoordinate without requiring GitHub Enterprise. Why it matters to a startup CTO

GitHub’s native merge queue for private repositories requires Enterprise Cloud. The target team needs coordination without that upgrade.

 DecisionUse local hooks and a local merge gate.

Agents use main to discover each other’s merged changes.

 Tradeoff

Unmerged work is invisible to coordination. The current prototype works across worktrees in one local repository.
RequirementStart with one repository in the existing Codex workflow. Why it matters to a startup CTO

The CTO can pilot it with one engineer before rolling it out to the team.

 DecisionShip a Codex plugin.

MCP tools and setup skills connect IntentOS to an existing Codex installation.

 Tradeoff

Each machine needs a local install. Live implementation and coordination currently use Codex.
RequirementRun without provisioning a backend or database service. Why it matters to a startup CTO

A team without platform support can start the pilot on a developer’s machine.

 DecisionRun locally; store state in SQLite and files.

IntentOS has no hosted backend; model calls still go through Codex.

 Tradeoff

Runs use local CPU and disk. The team manages setup, updates, and backups, and the machine must stay available during a run.

The takeaway

Make intent explicit.
Make review easier.

Today

Where this can lead

If agents can understand intent and reliably verify changes against it, more of review can be automated. IntentOS is a first step toward that.
