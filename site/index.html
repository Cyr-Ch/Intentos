Why IntentOS

Green CI is not the same as a safe change

Coding agents are good at making tests pass. They are not good at knowing which rules your team never wrote down, which tickets should not be built, and what landed on main while they were working. Every number below is from our published evaluations.

21

Passes the tests, breaks the business

Who it is for

Built for the person who owns main

IntentOS is for established Python codebases where years of decisions live in tests, documents and closed tickets, and where coding agents are now doing real work in parallel.

Primary user

The tech lead of an established Python codebase

You know the rules. The agents do not. You are the one paged when a green PR breaks billing.

  • Rules mined from your own tests, fix commits and docs, each backed by a hidden test
  • Every run cites the evidence it used and the invariants it held
  • Vague and already-solved tickets end in a clarification or an abstention, not a diff
Rolling out agents

Platform and developer-experience teams

You need one place per repository to say what is protected, what blocks, and who approves what.

  • A trusted policies/<repo>.yaml in version control, never inside the target repo
  • Review tiers 0, 1 or 2 computed from the diff, with head-bound named approvals
  • Optional container-isolated verifier that fails closed
Reviewing agent work

Maintainers receiving agent pull requests

You want to know why a change was accepted before you open the diff.

  • A report per run: acceptance tests, invariants, architecture rules, scope, precedents followed
  • A merge gate that re-verifies the branch on the main of right now
  • A guardian that bisects a red main to the culprit merge and opens a validated undo PR
Not a fit today:

Greenfield projects with no history to learn from. Repositories that are not Python with pytest (the indexer, miner and verifier are Python-first). Teams that want the agent to approve its own rules.

How it works

From a ticket to a change you can defend

Five stages. Codex does the implementing. IntentOS does everything around it: what the agent is told, where it works, how its output is judged, and what reaches main.

01Learn the repository 02Compile the contract 03Build in isolation 04Verify independently 05Merge through the gate
01 · Learn

A world model of your repository

One onboard indexes symbols, imports, tests, documents and ticket history into a versioned graph bound to the commit. Then a second model mines your business rules from fix commits, rule-like tests and must/never sentences in your docs. Every candidate reference is checked against the repository and its test is run before anyone sees it.

  • Closed issues and the PRs that resolved them become precedents, re-linked through renames at every index
  • Approved rules live in a trusted YAML file outside the target repository
explain · evidence pack · demandlib @ 32b6cc5
# reusable symbols SY oemof.demand.tools.add_weekdays2df must_reuse src/oemof/demand/tools.py:50 SY oemof.demand.bdew.ElecSlp consider src/oemof/demand/bdew/elec_slp.py:18 # bound invariants · approved policy, one hidden test each INV-001 add_weekdays2df(holidays=[]) emits no warning, no weekday equals 0 INV-002 negative VDI 4655 factors warn; load curves stay non-empty # precedents · historical evidence, never policy EV-9500bc #43 "Warn when a profile is created without holidays" ← PR #100 · current changed set_holidays_in_df · added 2 tests
02 · Contract

Every ticket becomes a compiled change contract

A read-only planner turns the ticket and the evidence pack into requirements, each citing evidence IDs, plus the symbols to reuse, the paths it may touch and the checks that will run. A deterministic compiler rejects fabricated evidence, catch-all paths, unknown commands and attempts to make protected paths writable.

  • Three routes: implement, clarify with a blocking question, or abstain with cited reasons
  • Acceptance tests are written by a different model before implementation and must fail at base
contract.json · validated · 0 compiler errors
{ "route": "implement", "base_revision": "32b6cc5", "requirements": [{ "text": "Overlapping day categories raise a ValueError naming both categories", "evidence_ids": ["EV-9500bc", "EV-1a77f0"] }], "reuse": [{ "symbol_id": "SY:oemof.demand.tools.add_weekdays2df", "action": "must_reuse" }], "invariants": ["INV-001", "INV-007"], "allowed_paths": [ "src/oemof/demand/particular_profiles.py", "tests/**" ], "verification": ["pytest_project", "pytest_hidden_task", "pytest_invariants", "scope_check", "architecture_rules"] }
03 · Build

The agent works alone, but not blind

The implementer is a separate Codex thread in a detached Git worktree with its own CODEX_HOME. Your checkout and your global Codex configuration are never touched. Coordination hooks run after every command: when main renames, moves, removes or re-signs a symbol the agent uses, it is told the commit, the file and line, and the first step.

  • A stale tree cannot finish: the Stop hook refuses until the branch is synced
  • Hidden tests, policy and run artifacts live outside the worktree
hook · PostToolUse · worktree run-20261028-7c3e
While you were working, main changed: oemof.demand.tools.add_weekdays2df was renamed to annotate_weekdays in commit 4f1a2c9. Your code uses it at src/oemof/demand/particular_profiles.py:88. Update the import and calls, then bring main into your branch before finishing.

04 · Verify

Judged by checks the agent never saw

Verification runs from a snapshot of the worktree with trusted commands from the policy: the project suite, hidden acceptance tests, hidden invariant tests, deterministic AST architecture rules, a scope check and architectural-surprise signals. The agent's "all tests pass" is stored and ignored; status comes only from executed checks.

  • Machine-readable findings go back to the same thread for at most two repairs
  • Forged test reports are detected; a missing hidden test fails closed

05 · Merge

A gate that merges onto the main of right now

merge opens a PR with a review tier computed from the diff (0, 1 or 2 humans; at least one whenever IntentOS asked for review), takes head-bound approvals from the names you give, merges the branch onto current main, re-runs the hidden tests on the merged result, then fast-forwards main and records it in a ledger.

  • A green branch that uses a symbol main just renamed is refused with the exact fix
  • If main is red anyway, guard bisects to the culprit merge, names its partner, and opens a validated undo PR

What you get

The parts that make it hold up

⚖Rules mined by a second model

The model that writes the rules is never the one that later implements under them. Set INTENTOS_MINING_MODEL or say "mine with gpt-6-astra". Candidates without a passing test are never approved.

⌁Precedents from ticket history

Closed issues, the PR that fixed each one, and what it changed, linked to today's code and marked current, partially stale or stale. The planner may cite them; the verifier reports whether the diff followed them.

◫Acceptance tests before the code

A different model writes the ticket's acceptance tests in a read-only thread. They must fail at base, they are kept outside the worktree, and the implementer never sees them.

⇄mergeguard coordination

Deterministic, no model inside: AST diff of main against the worktree's imports, sync notes, a Stop gate, review tiers, merged-result verification, a ledger, and a guardian that bisects and undoes.

▤Local dashboard

Live runs with the pipeline stage and event timeline, the repository's policy with inline editing, the knowledge base of evidence and precedents, and per-role model and skill settings. Localhost only.

✳One-sentence operation

"Set up IntentOS for this repository" runs the setup skill end to end. Afterwards status tells Codex which tool comes next. Approver names come from you; the model cannot invent them.

Security and trust

The model proposes. It never gets to decide.

Every authority boundary in IntentOS is enforced in code, not in a prompt. These are the properties the test suite checks.

  • Your base branch never changesImplementation happens in a detached worktree; the verifier checks its HEAD still equals the base before trusting anything.
  • Ground truth is out of reachPolicies, hidden tests and run artifacts live outside the worktree and outside the target repository. The compiler refuses to make protected globs writable.
  • Only trusted commands runVerification commands are id → argv entries in the policy; model output can only name an ID. No repository text ever reaches a shell.
  • Model claims are inertA fake "all tests pass" does not change the outcome. Forged JUnit reports are caught by a static inventory cross-check and a forbidden-names rule.
  • Approval needs a personThe MCP tools that change policy are app-only and require a widget token the model never receives. Auto-approved rules are labelled auto:<model> so the trade-off is visible.
  • Fail closed, optionally in a containerWith INTENTOS_VERIFIER=docker candidate code runs with no network, a read-only root, dropped capabilities and limits; if Docker is missing nothing falls back to the host.
Install

Three commands, then one sentence

IntentOS ships as a Codex plugin: an MCP server plus the intentos-setup and intentos-policy-mining skills. The checkout is its own local marketplace.

zsh
# get the plugin
$ git clone https://github.com/Cyr-Ch/Intentos ~/intentos
$ cd ~/intentos && npm install && npm run setup:python

# register it with Codex
$ codex plugin marketplace add ~/intentos
$ codex plugin add intentos@intentos

# in the repository you want to bring under IntentOS
$ codex
> Set up IntentOS for this repository

The setup skill checks the installation, registers the server, onboards the repository, mines its rules with a model other than the session's, loads ticket history if you give it a GitHub repo, and confirms a first run can start. It asks you only for what it cannot know.

Requirements

  • Node.js22.6 or later. The sources run without a build step.
  • Python3.11 or later with venv. pytest is installed into .intentos/venv.
  • Git2.30 or later, for worktrees and rename detection.
  • CodexThe Codex CLI or app with a signed-in account or CODEX_API_KEY.
  • OptionalDocker for the isolated verifier; the gh CLI for ticket precedents.

FAQ

Questions we get

Does IntentOS replace code review?

No. It decides how much review a change needs (tier 0, 1 or 2) from what the diff actually does, and it hands the reviewer a report of what held: acceptance tests, invariants, architecture rules, scope and precedents. A change that only touches documentation or adds code may merge with no human; a change to a protected path or an existing test always needs two.

Does the agent get to approve its own rules?

No. The MCP tools that change policy are visible only to the host's UI and require a session token the model never sees. The rules are mined by a model other than the one implementing, every reference is checked against the repository and every invariant must come with a test that passes at the current revision. If you choose the no-review path, each rule is written with approved_by: auto:<model> and carries blocking authority, which the output tells you plainly.

Which languages and hosts does it support?

Python repositories with pytest today: the indexer is AST-based and the verifier runs pytest in the repository's own virtual environment. Codex is the primary host (plugin, skills, elicitation forms in the CLI, the review widget in the app). Any MCP host can call the tools; hosts that render MCP Apps, such as Claude or VS Code, get the review as an inline widget.

What does it cost per run?

In the mergeguard evaluation the Codex arm paid about 16 seconds, 2.9 tool calls and 388 output tokens more per run than raw git. In the demandlib batch IntentOS used 21% fewer tokens overall, mostly because its runs needed half the repairs. Onboarding a repository and mining its rules is a one-time cost of a few minutes.

What happens when a rule is wrong?

A wrong blocking rule stops every run in its scope until you edit it. Rules live in one YAML file under version control; the dashboard's Policy tab edits a rule's statement or switches it between blocking and advisory, validates the file and re-indexes. Nothing is hidden in a database.

Can I try it without Codex credentials?

Yes. The offline mode replays a known-good or known-bad patch through the full pipeline against the bundled fixture, so you can watch the gates work: the bad patch passes the project's own tests and is still blocked by an invariant, an architecture rule and the hidden acceptance tests.

What does mergeguard miss?

A change of meaning behind an unchanged signature. The sync check is an AST comparison, so it cannot see that a function now returns cents instead of dollars. That is why the gate also runs the hidden tests on the merged result before main moves, and why the guardian exists for the cases that still get through. The evaluation reports that blind spot rather than hiding it.
